# Linux 入侵排查：三条线，一个 `/proc`

> 一台机器被入侵了，你从哪开始查？

## 起因

拿到一台"疑似被入侵"的 Linux 服务器，SSH 登录权限。**没有其他信息。**

大多数人第一反应是 `top` 看 CPU —— 然后漏掉一半。**因为不同类型的东西，暴露方式不一样。**

## 三条线

只查一条必然漏。**三条都要走。**

| 类型 | 开端口？ | 吃什么 | 查什么 |
|---|---|---|---|
| 后门 / 反弹 shell | ✅ 有 | — | **`ss -tlnp`** |
| **挖矿程序** | ❌ **不开** | **CPU** | **`ps aux`** |
| **自我删除的进程** | ⚠️ 可能 | — | **`lsof \| grep deleted`** |
| 键盘记录器 | ❌ 不开 | 磁盘 | `lsof` 看写的文件 |

```bash
# ① 谁在吃 CPU
ps aux --sort=-%cpu | head -5

# ② 谁开着门
sudo ss -tlnp

# ③ 谁拿着已删的文件
lsof | grep deleted
```

**⚠️ 挖矿程序通常不开端口 —— 只查 `ss` 会完全漏掉它。**

## 怎么看输出：可疑度判据

| 观察 | 判据 |
|---|---|
| `COMMAND` 带方括号 `[kworker/0:1]` | ✅ **正常** —— 真内核线程 |
| 名字像内核线程但**没方括号** + 高 CPU | 🔴 **高度可疑** |
| 路径在 `/tmp/`、`/dev/shm/`、隐藏目录 | 🔴 |
| 监听端口是 `31337` / `1337` / `4444` | 🔴 攻击者的经典默认值 |
| 绑 `0.0.0.0` 而不是 `127.0.0.1` | 🔴 **对外开门** |
| 有 `(deleted)` 标记 | 🔴 自我删除 |

**最后一条判据最重要**：

> **"看着奇怪"不是判据。要能指出具体哪一点可疑。**

`0.0.0.0` 和 `127.0.0.1` 的区别就是典型：

- `127.0.0.1:8080` → 只有本机能连 → 相对安全
- `0.0.0.0:8080` → 任何能访问到这台机的人都能连 → **对外开门**

## 拿到可疑 PID 之后：全部通向 `/proc`

```bash
ls -l /proc/<PID>/exe     # 它真正在跑哪个文件 —— 路径常暴露一切
ls -l /proc/<PID>/cwd     # 它站在哪个目录
ls -l /proc/<PID>/fd      # 它打开了什么（socket、已删文件都在里面）
cat /proc/<PID>/status    # 详细信息
```

**`exe` 和 `cwd` 为什么价值高**：攻击者改名很容易，但**工作目录和真实路径很难藏**。
一个叫 `kworker_raid` 的进程，`cwd` 指向 `/tmp/.cache_update` —— 一眼就露了。

**⭐ 同一对象，用不同工具从不同角度看 —— 对上了才可信。**

程序能改自己的名字（伪装成 `kworker`），但改不了 `/proc/<PID>/exe` 指向的路径。

## 反向思路：为什么"监听"比"外连"更值得盯

一个后门进程**不主动连任何人**。它只是：

```
攻击者 ──── 连进来 ────→ 这台机器上的后门进程
```

**机器本身没有任何异常出站流量。** 防火墙、出站监控全都看不到。

**→ 所以防御方必须盯"谁在监听"，而不是"谁在往外连"。**

## 处理

```bash
kill <PID>        # 先发 SIGTERM，给它体面退出的机会
kill -9 <PID>     # 不行再上这个
```

**为什么要分两步**：

- `SIGTERM`(15) —— 进程可以**捕获**它，先保存数据、清理临时文件，然后退出
- `SIGKILL`(9) —— **无法捕获**，内核直接收走。进程没机会收尾

**`kill -9` 是最后手段，不是常用手段。**

**bash 会用不同的词报告这两种结果：**

```
[1]+  Terminated    sleep 400     ← kill（SIGTERM）
[1]+  Killed        sleep 400     ← kill -9（SIGKILL）
```

## ⚠️ 排查时的一条铁律

> **先查清楚，再动手杀。**

**杀了它，线索就断了**：

- 它打开的 fd 全部关闭
- `(deleted)` 的文件从 `lsof` 里消失
- 内存里的状态没了

**正确顺序：确认它从哪来 → 干了什么 → 有没有同伙（`crontab`、`systemd`）→ 最后才杀。**

## 完整清单

```bash
# ========== 第一步：三条线 ==========
ps aux --sort=-%cpu | head -10
sudo ss -tlnp
lsof | grep deleted

# ========== 第二步：深挖可疑进程 ==========
ls -l /proc/<PID>/exe
ls -l /proc/<PID>/cwd
ls -l /proc/<PID>/fd
cat /proc/<PID>/status

# ========== 第三步：找同伙（进程会重启） ==========
crontab -l
sudo ls -la /etc/cron.d/ /etc/cron.daily/
systemctl list-units --type=service --state=running

# ========== 第四步：处理 ==========
kill <PID>
kill -9 <PID>          # 如果上面无效
```

**⚠️ 第四步的顺序很重要**：**只杀进程，不管自启项 —— 它下次开机（或定时任务触发时）会回来。**

## 一句话总结

> **挖矿看 CPU，后门看端口，自我删除看 `(deleted)`。**
> **三条线都要走，深挖全靠 `/proc`。**
> **先查清再杀 —— 杀了线索就断了。**
